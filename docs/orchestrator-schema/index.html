Orchestrator Turn Schema

One request, end to end — admission to publish — with the react loop restructured so the governor decides what a round is for before the round runs, and open gaps are the state that carries through it.

Owner chat seat (orchestrator) Supersedes the implicit flow in run_pipeline Live facts read from mobius-chat-00982 Date 2026-09-10
live — exists today changed — exists, behaves differently new — must be built defect — known, named, not yet fixed

This document exists because two implementations of one idea drifted: the appeals tools were reachable through react_loop and tool_agent, and only one door was hardened. A seven-step loop across five seats will reproduce that at scale unless the steps, their owners, and their inputs are declared once. That is this page's only job.

Handoff

livenow measured

The gap between processes. Until today nothing measured it, because the two sides hold different clocks: posted_at is wall-clock UTC and crosses processes; t0_start is a perf_counter and is process-local. They cannot be subtracted — so both are recorded and their difference is the queue wait.

Queue wait, first measurement

0.023smedian across 16 turns — the two clocks agree to ~23ms on the warm path.

…and it is bimodal

3.67sp90. Twelve turns sit at ~0.02s, two at ~3.9s. Two regimes, not a tail — a p50 alone would call this negligible and be wrong about one turn in seven.

The react control loop

restructured

The change is one inversion: the governor stops being a brake and becomes the scheduler. Today it is consulted at the end of a round to decide whether to grant another. In v2 it decides at the top what the round is for, and the loop terminates on gaps closed rather than on rounds exhausted.

The socket already exists and is already load-bearing. A round-top governor call runs today at react_loop.py:4729 and shapes the round's agent_role and reasoning_depth. It does not select tools, choose the model, or gate continuation. v2 extends a live call site rather than introducing one — which is why this is smaller than it looks.

One cycle · repeats until no gap is open or the governor stops it

state carried: open gaps
  1. 1

    Governor sets the round changedgovernor seat

    Reads open gaps · time left · quality so far · cost so far and emits a directive plus a budget for this round. Continuation is decided here and only here.

  2. 2

    Select tools per gap newtool_manifest seat

    Choose the tool that closes this gap, not the tool that fits the question. The manifest is rendered for the selected set, not the catalogue.

  3. 3

    Build the prompt for the intent changedchat seat

    Composed from the directive and the selected tools — the round's purpose, not a general system prompt reused every round.

  4. 4

    Select the model newllm_manager seat

    Chosen for this round's work and budget. See the open question below: prompt size and model choice constrain each other.

  5. 5

    Call livechat seat

    The model returns a tool choice and arguments.

  6. 6

    Execute the tool livechat seat

    Dispatch, retry policy, and the three-state result verdict — content, declared absence, or nothing.

  7. 7

    Classify into memory · update gaps newunassigned — see §7

    The result closes a gap, narrows one, or opens a new one. This step is what makes the loop terminate, and it is the step with no owner today.

One of four inputs is live. A governor that steers on time and fakes the other three is worse than one that admits it steers on time — so steps 2, 4 and 7 land after cost and per-round quality, not before.

What the restructure retires

The two-writer extension defect defect

Today the completion critic and the governor both grant extensions from one shared ledger, reading the same env var with different defaults (90 vs 120) and different margins (5s vs 25s). Making the governor the only actor that decides continuation removes this rather than fixing it.

The manifest's unconditional cost

58 tools rendered every round, ~36% of the react prompt. Per-gap selection makes the reduction real without anyone having to decide which tools are dead — a far safer mechanism than pruning a static list.

Exit

livestructure is a defect

Three publish terminals reached from eight call sites — and the eight differ only in how deep in the try-nest the turn stopped, not in outcome.

TerminalCall sitesReality
_publish_completed4Live. Also carries the early return on an empty payload, which gets its own outcome — a turn that delivered nothing is not completed.
_publish_failed4Live. Takes no ctx, so the outcome is marked at each call site.
_publish_clarification…0Unreachable. 209 lines, no callers. Orphaned by the refactor that deleted the classic path.

Dead at both ends. Nothing anywhere sets needs_clarification, needs_route_clarification, route_clarification_choices or clarification_message, and every read of all four sits inside the unreachable terminal. A consumer with no producer — the mirror of the defect this program has catalogued twelve times, and harder to see, because a falsy default makes an absent producer look like a legitimate negative.

08
worker

Close

live

The attestation closes in run_pipeline's outermost finally — one site, covering all three terminals and every early return. Writing it inside _publish_completed would leave every failed turn, every empty-payload turn and every unreached exit with no record, which is the emit sitting on the success path where the missing row is the valuable one.

promised 31s · delivered 19.7s · kept        → turn_attestations (system of record)
                                            → turn_completed envelope (what the trace shows)
                                            → jsonPayload.event=turn_attestation (log)

Verified on the deployed build: 14 turns, 14 rows, 0 duplicates. The finally fires exactly once across every exit those turns took.

Open questions — decide before anyone writes code

#QuestionWhy it blocks
1Who owns the gap object? Opened by whom, closed by whom, on what evidence.The loop terminates on "no gaps open". That is only as trustworthy as the thing that closes gaps — and an unread close is this program's most-repeated defect.
2Does prompt size constrain model choice, or the reverse? Step 3 precedes step 4.Token budget and manifest size differ per model. If the arrow is not declared, two seats will implement opposite answers — exactly the two-door failure this schema exists to prevent.
3Per-gap or per-round tool selection? One tool per gap, or one set for all open gaps.Changes whether step 2 runs once or N times per cycle, and therefore what step 5 is given.
4What happens to a gap that will not close?Without a give-up rule, "terminate on no gaps open" is an infinite loop with a round cap as its only real bound — which is the behaviour v2 set out to replace.
